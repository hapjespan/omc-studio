# 0036: Let Tekenen move one Cluster, Activity or Item to another parent with Shift, confirmed, as its own structure request

Date: 2026-11-18
Status: accepted (product owner, source point 53 and answers QS-1 to QS-7, 2026-11-18); QS-8 and QS-9 recorded as assumptions, to be confirmed by the product owner (`specs/001-omc-studio-v1/plan.md`). Amends H12, addendum K13, 6.2 and 6.3, kickoff v1.2 6.5.7, SD-29 for this move, ADR 0014 and ADR 0021.

## Decision

In Tekenen, dragging one block with Shift held and releasing it over another parent moves it there: a Cluster (with its Activities) to a Domain, an Activity to a Domain or a Cluster (also into or out of a Cluster within its own Domain), an Item to a Group; always within the same kind of Area (activity Areas among themselves, list Areas among themselves). A Domain is only slid within its own Area; moving it to another Area stays in Invoeren. A Shift-drag acts on the one block under the pointer, so several blocks are never moved at once. Without Shift a block stays inside its parent. Every move is confirmed first in a dialog "Verplaatsen naar <doel>?", also through the panel field "Verplaatsen naar" (SD-42); undo and redo ask too (assumption QS-9); cancelling stores nothing and puts the block back. The block keeps its size and style and stays where it was released, pushed inside the target's width if it sticks out at a side; a block wider than its target is made as wide as the target, its Manual children pushed left and narrowed, and the user is told (assumption QS-8). The confirmed move is one request, queued with the automatic saves, carrying the structure and Layout versions and the block's Layout relative to its new parent. The server runs the structure service's move, which changes structure only, with the rules of Invoeren (FR-037, FR-043a); unlike "Hangt onder", which resets the subtree to automatic, the Shift move keeps the subtree's Layout rows, checks the Layout like any Layout, writes parent, order and Layout in one transaction, raises both versions, audits old and new "Hangt onder" and the Layout, and returns both versions. Allocation lines stay on the moved identifiers; a Finalised year does not block it. The Layout save keeps refusing any parent that differs from the structure, and the drawing library never reparents a node by itself (WP-E0 P5, P10).

## Motivation

The product owner wants to regroup the picture where they see it, without switching to Invoeren, and wants every such regrouping confirmed because it moves amounts between Domains. One move service for both modes keeps H2 to H4, the same-kind rule and the Target rule in one place (constitution III), and a separate request keeps the Layout save a pure Layout check, so a malformed save still cannot smuggle a structure change in. Keeping the block where it was released is the product owner's choice over addendum 6.2 and SD-29. Rejected: new parents inside the whole-Layout save (structure and Layout rules in one payload, and the H12 bypass check could no longer tell a move from tampering) and moves without confirmation (the advice, overruled).
